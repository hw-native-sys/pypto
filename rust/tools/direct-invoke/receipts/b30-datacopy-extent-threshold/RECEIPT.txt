sweep does settle: 4, 8 and 16 bytes all fail and 32 passes. The *at-least-32* reading is

different ones. B30's threshold may now be stated as `>= 32 B`, where it previously had to

say what the tile holds** — that still needs the whole destination dumped rather than

`all-20-element1-runs.txt`. Same host, harness, oracle and kernel; the index is read from
element 1 instead of element 0 (`__v0 = 0` -> `__v0 = 1`, the only use of `__v0`), so
`got` inverts to what element 1 held. ORACLE 44's input block already places a **decoy

|---|---|---|---|

**My own narrowing argument for 79 was wrong, and so are both replacements.** The argument
I had made -- that a wider sub-block copy would leave different stale content -- is invalid
for the reason chip-agent gave: the kernel's only observable was element 0, and element 0's
stale content cannot depend on how many elements *past* it were requested. So the identical
value across my 4/8/16 B arms was a property of the read.

But the discriminator built on that correction **does not separate the two candidates
either, because neither survives**:

* *"No copy happens at all below one block"* predicts element 1 **identical in every arm**.
  It is not: 0.0 at 4 B, mixed at 8 B, 0.5 at 16 B, 0.0 at 32 B.
* *"A partial transfer that did not write element 0"* predicts element 1 = the decoy for
  `n >= 2` and **not** for `n = 1`. The observation runs the **other way**: the 1-element arm
  shows the decoy value and the 4-element arm does not.

**And the sub-block behaviour is NOT deterministic.** The 8 B arm returns 0.0 twice and then
0.5 three times, in one session on one chip. It **flips once** rather than alternating, which
is a transition and not 50/50 noise -- and the first-two-reps-differ shape is B14's. That is
a caution I am recording against my own work, though it does **not** disturb the element-0
clearance: that sweep was 5/5 identical in all four arms, and this is a different observable.

**The 0.5 recurs.** It is the same stray value B30 decoded at element 0, now appearing at
element 1 in two arms. A value that repeats across extents and across elements looks more
like a fixed residual than like random garbage -- but that is a reading, not a measurement,
and nothing here says what the tile holds.

**So 79 is reshaped, not closed, and it is harder than it looked.** The instrument that
remains is the one it always named: dump the WHOLE destination tile rather than read one
element, which separates *uninitialised* from *stale* and would say whether 0.5 is resident
before the copy. Reading element 1 was cheaper and has now been spent; it bought two
refutations and a non-determinism, which is more than the closure it was aimed at.

ADDENDUM 2026-11-09 (third) — IT IS THE COMPILER, AND THE PAD REPAIRS IT
================================================================================

NM 87 asked whether the hardware fails to write a sub-block copy or `bisheng`
never emits a DMA for one. Neither, exactly: the instruction IS emitted, with a
length ROUNDED DOWN to a multiple of 32. Files: nm87-encoding-table.txt,
pad-9-runs.txt, pad-sources.txt, run_pad.sh, gen_pad.py.

HOW TO GET AT THE DEVICE CODE. `-save-temps` SEGFAULTS the bisheng frontend under
`-x asc` (exit 139 in clang::CompilerInvocation::CreateFromArgsImpl, clang
15.0.5) -- do not spend the attempt. What works: the fused `main.asc.o` carries a
`.aicore_binary` section, extractable with
`objcopy --dump-section .aicore_binary=out.bin`. The device compile line comes
from `cmake --build ... -- VERBOSE=1`.

THE ENCODING, 19 extents from ONE generator differing in the copy-extent literal
alone, COMPILE ONLY (nothing above 8 f32 was launched -- those would be a UB
out-of-bounds write past InitBuffer(tbuf0, 32)):

    n       req B    .aicore_binary md5   field at off 629
    1..7     4..28   cf4a419a4ddd         0x07061A10
    8..15   32..60   d1337d5d5427         0x10061A02
    16..23  64..92   861bc5cf91a2         0x10063A02
    24      96       87b9600c7990         0x10065A02
    32      128      dcdc45fb1148         0x10067A02

  * n=1..7 compile to the BYTE-IDENTICAL device binary: 4 B and 28 B are the same
    code, so the extent does not reach the instruction below one block.
  * n=8..15 are likewise byte-identical TO EACH OTHER, so 36, 40 ... 60 bytes
    compile to the same code as 32 and lose the remainder.
  * The field advances once per 32 bytes. Encoded length = requested bytes
    rounded DOWN to a multiple of 32, which for any sub-block extent is ZERO.
  * TWO CAVEATS. "Offset 629 is the length" is an INFERENCE from a 3-byte diff
    plus a perfect correlation across 18 extents and five values, not a
    disassembly; `/usr/bin/objdump` does not know DAV ISA. And the n=64 row must
    NOT be folded in: its binary differs from every other, so the instruction
    sequence changed and that offset is no longer the length field there. Valid
    for n <= 32 only.

SO B30 IS A TOOLCHAIN ROW, NOT A SILICON ROW. The DMA engine was never asked to
move anything. "The value is present in neither buffer" was a length-0 transfer.

AND THE SYMMETRIC REPAIR WORKS. The emitter's sub-block refusal said it did not
pad because "the load-side pad has not been measured on this part, and one ORACLE
44 probe would settle it". Run, as a same-build A/B with the poison prologue so an
un-delivered cell is distinguishable from a delivered one, reading element 0 -- the
index -- so the ORACLE's OWN VERDICT answers:

     4 B via DataCopyPad    PASS  wrong=0      3 of 3   the index arrived
    32 B via DataCopyPad    PASS  wrong=0      3 of 3   the pad itself is sound
     4 B via plain DataCopy FAIL  wrong=5120   3 of 3   poison 2.0 intact

Same kernel, same poison, same element, only the API differing. A load-side
`DataCopyPad` DOES deliver a 4-byte GM->UB copy on this part.

(Reading note: on a PASS the oracle prints no `got ... want` line, so a script
grepping for `got` reports "no readout" on exactly the runs that succeeded. The
PASS and wrong=0 are the signal; the blank is the script's.)

WHAT LANDED IN THE EMITTER. The refusal became a `DataCopyPad` branch, and the
predicate widened from "below one block" to "NOT A WHOLE NUMBER OF BLOCKS" --
because a 36-byte load is not sub-block and still loses four bytes. Byte-neutral
on the corpus: all 124 constant-extent loads in the 105 stored artefacts are
already whole blocks, so ZERO artefacts moved and no recorded device PASS was
detached. The 145 runtime-extent load sites are deliberately NOT changed in the
same commit, and a test pins that scope so widening it is a decision rather than
a discovery.

ADDENDUM 2026-11-09 (fourth) — THE PAD REPAIR IS WITHDRAWN
================================================================================

The third addendum licensed a `DataCopyPad` repair on a probe that read ELEMENT 0
ONLY. That was the whole hole: nothing in it measured what the pad does to the
rest of the destination block. Measured now, and the repair does not survive it.
Files: nm89-33-runs.txt, run_nm89{,b,c}.sh, gen_nm89{,b}.py.

    arm                                 cell   result            runs
    4 B DataCopyPad, isPad=false        1      3.0  = GM[0]      3 of 3
    4 B DataCopyPad, isPad=false        2      3.0  = GM[0]      3 of 3
    4 B DataCopyPad, isPad=false        4      3.0  = GM[0]      3 of 3
    4 B DataCopyPad, isPad=false        7      3.0  = GM[0]      3 of 3
    4 B DataCopyPad, isPad=TRUE, pv=0   1      3.0  = GM[0]      3 of 3
    4 B DataCopyPad, isPad=TRUE, pv=0   7      3.0  = GM[0]      3 of 3
    4 B DataCopyPad, isPad=TRUE, pv=0   0      index delivered   3 of 3
    32 B DataCopyPad (control)          1      0.0  = GM[1]      3 of 3

A poison prologue had put 2.0 in every cell first, so 3.0 can only have come from
GM element 0. So a sub-block `DataCopyPad` LOAD fills the WHOLE 32-byte destination
block with element 0's value, and `isPad = true` with paddingValue 0 does not
control it. The 32 B control reads GM[1] correctly, which is what proves the
element-1 readout works under a pad at all.

ONE AMBIGUITY, not separated: "the block is filled with GM[0]" and "every read
aliases element 0" both fit, because the kernel reads one cell per build. Both are
disqualifying in the same way, so the verdict does not turn on it.

WHAT THIS MEANS. The pad trades a silent short READ for a silent block-wide WRITE
-- the same defect shape B30 is about. A tile whose rounded-up padding is later
read by a vector op would consume a replicated element 0 rather than whatever the
author expected. So the emitter's refusal is RESTORED, and `guarded_gm_load` is
deleted rather than left dead.

WHAT SURVIVES, and it is most of it:
  * The PREDICATE stays widened, from "below one block" to "not a whole number of
    blocks". That came from the encoding read, not from the pad, and the
    neighbouring lane has already adopted it in the artefact gate.
  * The extent is now resolved from the MLIR CONSTANTS rather than from the
    stringified product, so the detector sees the 145 sites a C++-text scan calls
    "runtime". Byte-neutral: no stored artefact moved.
  * Every device and compile figure in the three earlier addenda stands. What was
    wrong was the inference drawn from one cell, not any measurement.
  * `quant_i8_v41_8x5120` is REFUSED again, not emitted. Its AscendC-side doubt is
    NOT resolved.

AND THE METHOD NOTE, because this is the second time the same shape has bitten in
one day: a probe that reads ONE cell cannot license a claim about a BLOCK. The
first instance was reading element 1 and concluding about the copy; this was
reading element 0 and concluding about the repair. The fix both times was another
arm, and it cost three builds.

CORRECTION TO THE THIRD ADDENDUM'S TABLE, from two independent readers: the
`field at off 629` column read as an LE-u32 is not a length. It COLLIDES between
req=4..28 and req=256 (both 117833744) while their md5s differ, and it does not
reproduce under a different build configuration. Read as a SINGLE BYTE it is
literally floor(bytes/32)*32 -- 0x00 / 0x20 / 0x40 / 0x60 / 0x80 -- which does
reproduce. The load-bearing facts are the BYTE-IDENTITY GROUPINGS of
`.aicore_binary` (1..7 one group, 8..15 another, and a constant section size of
3576 B across 1..63 so only an immediate moved); "encoded length 0" is an
interpretation of those, and the md5 values themselves are configuration-dependent
and must be quoted as relations, never as constants.

ADDENDUM 2026-11-09 (eighth) — IT IS A FILL, NOT AN ALIAS
================================================================================

The fourth addendum left one ambiguity it could not separate: a 4-byte
`DataCopyPad` load leaves cells 1..7 reading element 0's value, and that fits BOTH
"the block was filled with element 0" and "every read aliases element 0". One cell
per build cannot tell them apart. The discriminator costs one line and no new
oracle id: overwrite ELEMENT 0 ONLY after the pad, then read cell 1.

    buf0.SetValue(0, 1.0f);   // after the pad, with barriers either side

    arm                      reads   result                      runs
    alias_1                  cell 1  3.0  = GM[0]  -> PASS       3 of 3
    alias_c0  (same build)   cell 0  1.0  = the SetValue, FAIL    3 of 3

  * FILL, NOT ALIAS. Cell 1 does NOT follow element 0 to 1.0, so the cells hold
    their own copies of element 0's value, written at copy time. An alias would
    have tracked the overwrite.
  * THE CONTROL IS IN THE SAME BUILD. `alias_c0` differs only in which cell it
    reads and shows 1.0, so the `SetValue` demonstrably landed -- without it, "cell
    1 did not change" could equally have meant the overwrite never happened.
  * Both 1.0 and 3.0 are legal indices for a 4-row table, so neither path can
    fault and the fault ambiguity of the 1e30 prologue does not return.
  * TWO MORE CANDIDATES DIE WITH IT: a read-modify-write of the block from GM would
    put GM[1] = 0.0 into cell 1 (which is exactly what the 32 B control reads), and
    a zero fill would put 0.0 there. Neither is observed.

So the mechanism of the load-side pad is now: it writes element 0's value into
every cell of the destination 32-byte block. That is a FILL with a definite value,
not undefined content, not a wider GM read, and not an addressing artefact.

ADDENDUM 2026-11-09 (ninth) — THE GUARD IS CALIBRATED, AND THE 2x2 CLOSES

The seventh addendum reported `guard_breach = 0` in nine of nine and NO ARM EVER

                  plain DataCopy            DataCopyPad

than the one this lane was weighing. Not correctness: THE REPAIR HAS NO
BENEFICIARY. Over the stored artefacts there are zero constant-extent
partial-block sites, the smallest constant extent is exactly 32 bytes, and ZERO
kernels are refused on this ground -- the only kernel that ever hit it, the decode
embedding's 1x1 index read, was fixed at the SOURCE to load a whole block. So the
refusal blocks nothing and costs nothing, while the pad would be licensed by a
precondition about today's emitter whose failure mode is a WRONG ANSWER rather
than a refusal. A capability nothing uses is not worth an unenforced invariant.

The precondition audit is now an ENFORCED TEST rather than a one-time reading:
`ascendc_emit/tests/the_pad_precondition_is_enforced_not_audited.rs`. It fired on
its first run, on `((({}) + 7) / 8) * 8` -- the same round-up with the division
parenthesised differently -- which also reconciles the two counts of allocation
sites: 106 in five shapes, and the 106-vs-108 gap was a regex truncating at 200
characters rather than a disagreement about the code.
