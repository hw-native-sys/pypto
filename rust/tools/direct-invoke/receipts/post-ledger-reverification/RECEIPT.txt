So the number is unauditable in both directions: I cannot re-derive it and neither
can the lane that produced it. Two structural reasons, both measured:

  * `~/.claude/skills/flashrsi-kernel-coverage` IS NOT A GIT REPOSITORY. The
    scorer's only history is ad-hoc `.bak-` copies, and the one that printed the 39

    `skill: []`, `prompt: []` and `tool`/`config` naming only paths under that

    "the unit of promotion was blind to every edit the campaign had ever made" --

The campaign pins its corpus SHA, denominator, splits, tolerances and oracle. It
does not pin the thing that turns evidence into a number. A fixed scorer is the

unhashed, unrecorded instrument means no reading of this campaign is reproducible

ADDENDUM 3 -- WHAT THE COMMIT GATE CAUGHT ON THE WAY IN
--------------------------------------------------------
This receipt's commit was REFUSED by pre-commit, by
`test_bench_manifest_records_every_artefact.py::test_the_totals_block_agrees_with_the_rows_it_counts`
on all three scored corpora:

    deepseek_v41  totals.tile_rs = 4   rows carrying =  5   files on disk =  5
    glm_5_3       totals.tile_rs = 4   rows carrying = 11   files on disk = 11
    kimi_k3       totals.tile_rs = 8   rows carrying = 17   files on disk = 17

No manifest was dirty and all three totals matched HEAD, so no manifest edit caused
it. The mechanism is `_row_carries`' fallback: a row with no string claim for its
`.rs` is counted by `(root/sub/f"{stem}{ext}").is_file()`, so a file appearing on
disk moves the count with no manifest edit -- which is why `carrying` equalled the
file count exactly in all three.

Underneath it: `git ls-files --others` showed 17 of those `.rs` files UNTRACKED,
while `coverage_models.py` builds the tile_rs column by globbing the directory. So
the tile-rs half of C_b was read off one working tree. The ledger does not pin them
either -- across all 146 records there are ZERO `(artifact, sha256)` pairs whose
artifact ends in `.rs`; the C_b records pin the `.cpp` and list `rustc-compiles` in
`evidence.checks`, so the file that gate ran against had no recorded identity
anywhere. `components-pto-models.json` excluded `rust/bench/*/tile-rs/**` from the
harness roles on the stated grounds that "the evidence ladder already carries their
sha256 per kernel" -- false as written for every one of the 146 records.

A `git clean -fdx` would have taken C_b to about 16/72 with nothing in the ledger
showing it had been higher: the ledger loss one level down. The other lane owns
those artefacts and landed the repair -- an explicit `"tile_rs"` claim plus
`"tile_rs_sha256_16"` per affected row following the existing
`pto_sha256_16`/`ascendc_sha256_16` convention, totals -> 5/11/17, one
`"tile-rs": null` dropped where the gate then caught a two-spelling disagreement,
and that justification reworded against the zero-`.rs` count. This lane
deliberately did not `git add` them: staging into a shared index is how five of
that lane's files were swept into bf69b059b earlier today. The 18 `.rs` files
remain untracked pending the owner.
